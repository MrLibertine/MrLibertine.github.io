把 Flash + Starling 的《Hungry Hero》完整搬到 Cocos Creator 3.8

2026-11-01 Cocos Creator 3k 字
Cocos Creator 游戏开发 迁移 Flash

鼠标移动控制主角高度，吃食物加分，躲障碍。画面小就点右下角 ⛶ 全屏，或在新窗口单独打开。

《Hungry Hero》是 Hemanth Sharma 2012 年用 Adobe Flash + Starling 写的一个开源小游戏，跟着他的书一起放出来的，协议是 Simplified BSD。玩法很朴素：一个永远吃不饱的英雄往前飞，玩家用鼠标控制他的高度去吃食物、躲障碍，路上有咖啡（加速 + 撞穿障碍）和蘑菇（食物自动飞过来）两个道具。

我把它完整搬到了 Cocos Creator 3.8.8。不是「照着玩法重写一个」，而是把原来的五个类逐个对应过来：Welcome / InGame / GameBackground / Hero / Obstacle，连图集矩形、音效、动画帧序、背景视差系数都是原样的。

复刻了什么

原版功能 状态
欢迎页主角从左侧滑入 + 标题/按钮 保留，缓动曲线按原版 1.2 秒
5 种食物编队（波浪、直线、斜线、环形…） 按原 pattern 状态机逐个实现
4 种障碍物 + 出现前 “LOOK OUT!” 5 帧预警 保留，含红屏闪烁
撞击后主角翻转、扣命、屏幕轻微震动 保留（震动是相机节点位移）
咖啡加速 / 撞穿障碍、蘑菇自动吸食 保留，各自配粒子发射器
4 层视差背景（天空 0.02 / 山 0.2 / 楼 0.5 / 草 1.0） 与 BgLayer.as 完全一致，含取整与回卷
生命 5 条、分数 = 食物分 + 距离 保留
暂停、静音、About、结算页（MAIN / PLAY AGAIN / ABOUT） 保留，结算页按钮布局按原公式算

原工程里 assets/ 只有一张 2048×1024 的图集、两张 1024×768 的背景和 8 个 mp3，这些直接复用，一张图都没重画。

迁移策略：复用引擎包，运行时搭场景

Cocos 3.x 的常规做法是在编辑器里拖一个场景再构建，但那样产物是「场景资源 + 序列化 JSON」，我这边没有编辑器里的手工接线，也不想把一堆 .scene/.meta 手写出来（__type__ 要用压缩过的脚本 uuid，很容易写错）。

所以走的是「只复用引擎运行包，场景用代码搭」的路子：

  • 从之前那个 Cocos UI 性能实验室 里直接拿 cocos-js/（引擎本体）、src/system.bundle.js（SystemJS）、src/polyfills.bundle.js、import-map.json；
  • 写一个 index.js 入口，System.import('cc') 拿引擎，再 cc.game.init({settingsPath}) → cc.game.run() → 加载 src/game.js；
  • game.js 里 new Scene()、new Node()、addComponent(Sprite) 全部用代码建，最后 director.runSceneImmediate(scene)。

好处是整个工程就是几个纯文本 js + 一堆图片，改一行刷新就见效，也能在无头浏览器里跑自动化检测。

代价是：编辑器帮你做的事，全得自己补回来。下面就是补的过程里踩的坑。

五个「白屏但控制台零报错」的坑

这段是这次迁移最实在的部分。每一个都表现为「页面加载完了，画面什么都没有，控制台干干净净」。

1. 只建 Node 树，一个东西都不会画

场景图是完全正确的：director.getScene() 有 40 个节点，位置、尺寸、SpriteFrame 全对，sprite._renderData 也有 4 个顶点 6 个索引，requestAnimationFrame 在跑（getTotalFrames() 涨到 416），但 device._numDrawCalls === 0。

查了半天才在引擎源码里找到这句：

// cc.RenderRoot2D
onEnable() { director.root.batcher2D.addScreen(this); }
onDisable() { director.root.batcher2D.removeScreen(this); }

Cocos 3.x 的 2D 渲染是由 RenderRoot2D（Canvas 的父类）驱动的：它 onEnable 时把自己注册进 Batcher2D 的 _screens，渲染时只 walk 这些 screen。纯 Node 树再正确也不会被遍历。

所以必须有这一层：

var canvasNode = new Node('Canvas');
canvasNode.setPosition(DESIGN_W / 2, DESIGN_H / 2, 0);   // 放在设计区中心
scene.addChild(canvasNode);
canvasNode.addComponent(UITransform).setContentSize(DESIGN_W, DESIGN_H);

var camNode = new Node('Camera');
canvasNode.addChild(camNode);
var cam = camNode.addComponent(Camera);
cam.projection = Camera.ProjectionType.ORTHO;
cam.orthoHeight = DESIGN_H / 2;

var canvas = canvasNode.addComponent(Canvas);
canvas.cameraComponent = cam;      // Canvas 会把相机摆到自己的世界坐标 + z=1000

顺手记一下：Canvas._onResizeCamera() 会按 windowSize.height / getScaleY() / 2 重算 orthoHeight，所以设计分辨率适配是对的，不用自己算。

2. 相机参数写错了名字，而且不报错

我按记忆写了 cam.ortho = true; cam.nearClip = 1; cam.farClip = 3000;。全是不存在的属性，JS 不会报错，只是默默变成一个普通字段。结果相机保持默认的透视投影、near=1 / far=1000，而相机节点在 z=1000——所有精灵都在 z=0，正好落在远裁面上，被裁得一个不剩。

3.8 里正确的名字是：

cam.projection = Camera.ProjectionType.ORTHO;   // 0
cam.orthoHeight = DESIGN_H / 2;
cam.near = 1;
cam.far  = 3000;

排查手法是从 cc.director.root.device._numDrawCalls 反推：一直是 0，说明连提交都没提交，问题必然在相机/管线而不是贴图。

3. node.setScale(1) 会把节点变成隐形

这条最坑。原来 AS3 里是 hero.scaleX = hero.scaleY = 1，我顺手写成 heroNode.setScale(1)。看着天经地义，但 Cocos 的 setScale 期望 (x, y, z) 三个参数，缺的 y/z 会变成 undefined，局部矩阵直接退化成非数——节点还在场景里，activeInHierarchy 是 true，worldPosition 也能读，但就是不画。

更迷惑的是它的子节点也跟着坏：两个粒子发射器的 worldPosition 变成 NaN，我一开始以为是粒子系统污染了合批缓冲，绕了很久。

heroNode.setScale(1);                    // ✗ 隐形
heroNode.setScale(1, 1, 1);              // ✓
heroNode.setScale(new cc.Vec3(1, 1, 1)); // ✓

后来我在工程里全局搜了一遍 setScale，又抓出 setScale(p.scale) 和 setScale(w.scale, 1) 两处——都是缺参数的。

4. 运行时贴图：Texture2D.image 要的是 ImageAsset

图集是运行时用 <img> 加载的，随手写 texture.image = img 会炸：

TypeError: i.extractMipmaps is not a function

因为 image 的 setter 内部是 this.mipmaps = [t]，而 mipmaps 的 setter 会对每个元素调 extractMipmaps() —— 这只有 ImageAsset 上有。正确的包装是：

var imageAsset = new cc.ImageAsset();
imageAsset._format = 35;        // RGBA8888
imageAsset._nativeData = img;   // 注意：data 在这个构建里是只读 getter
var t = new cc.Texture2D();
t.image = imageAsset;
t.packable = false;

data 这个属性在 3.8.8 的 web 包里只定义了 getter（我试过 imageAsset.data = img，报 “only a getter”），所以直接写 _nativeData——data 的 getter 返回的正是它。

5. SpriteFrame.offset 的符号是反的

从 TexturePacker 的 XML 切帧时，裁剪帧要算 offset（裁剪后内容相对原图中心的位移）。我按「左上原点」的直觉写成：

f.offset = new Vec2(s.ox + s.w / 2 - s.ow / 2, s.oy + s.h / 2 - s.oh / 2);   // ✗

小图看不出来（差 1~3 像素），但背景层 bgLayer2 上下各裁了 26/44 像素，整层就往上错位 26px，接缝全露出来，看起来像一块块矩形贴错位置。

Cocos 的语义是：offset = 裁剪内容相对原图中心的位移，x 向右为正，y 向上为正；TexturePacker 的 frameX/frameY 是从左上角量起的负 padding。所以：

// offset.x = trimLeft - (ow - w)/2      trimLeft = -frameX
// offset.y = (oh - h)/2 - trimTop       trimTop  = -frameY
f.offset = new Vec2(-s.ox - (s.ow - s.w) / 2, (s.oh - s.h) / 2 + s.oy);

顺带两个 SystemJS 的坑

  • chunks/bundle.js（里面注册了 rollupPluginModLoBabelHelpers）必须用经典 <script> 标签加载，而且在 system.bundle.js 之后。它原本是给引擎 main 包的 preload 脚本用的，运行时模式下那段永远不执行，用 System.import() 去拉也不生效（我抓包确认过：一次请求都没发出去）。
  • 这套 SystemJS 里，相对的 ./xxx 是相对页面目录（document base），不是相对模块自己所在的目录。所以 src/application.js 里要写 System.import('./src/game.js') 而不是 ./game.js。

背景视差：照抄原版的两个细节

GameBackground.as 和 BgLayer.as 很值得抄，因为细节都藏在里面：

// 每层 = 两张同图，左边缘对齐在 0 和 w
image1.x = 0;            image1.y = stage.stageHeight - image1.height;
image2.x = image2.width; image2.y = image1.y;

// 整层左移，超过一个宽度就回卷
bgLayer.x -= Math.ceil(_speed * bgLayer.parallaxDepth);
if (bgLayer.x < -stage.stageWidth) bgLayer.x = 0;

两个要点：

  1. 底部对齐（stageHeight - image.height），不是垂直居中；
  2. 接缝要落在右边界上（第二张图的左边缘在 w）。我一开始按 x = 0 和 x = w 摆中心，接缝就跑到屏幕正中间去了——bgLayer2 是两边渐隐的软山丘，本来就不是为无缝平铺画的，接缝一进画面就是一条明显的亮带。改成左边缘对齐之后，接缝从右边界开始往左走，观感就回到原版了。

bgLayer4（草）我量了一下左右边缘像素：完全一致，能无缝平铺；bgLayer3（楼）最大差 8；bgLayer2 差得多——所以这条不是「代码 bug」，是素材本身的特性，照原版的摆法就不会难看。

运行时实测的数字

在无头 Chrome（SwiftShader 软件渲染）里跑起来后读引擎计数器：

场景 Draw Calls 三角面
游戏进行中（4 层背景 + 主角 + 30+ 食物 + 障碍） 12 ~ 13 164 ~ 234
结算页 12 150

因为所有精灵共用一张 2048×1024 的图集和同一个材质，食物/障碍/主角全被合进同一批；4 个背景层各自是一张图，拆成 4 批；再加大约 2 批动态字型的 HUD 文本。批次数几乎不随物体数量增长——这正是图集该有的效果。

顺便说一句，HUD 用的是系统字体 Label，每个 Label 实例都带自己的动态字型纹理。这里只有 6 个 label，代价可以不管；如果要做几十行的列表，还是得换位图字体。

设计分辨率与「视口」

页面用 SHOW_ALL 把 1024×768 的设计区等比塞进任意窗口，多出来的地方是黑边。但背景层是横向平铺的，会铺到设计区外面去，导致左右两侧露出来的内容和里面接不上——一条硬缝正好压在设计区边界上。

解决办法很土但有效：在最后一个兄弟节点上挂一个 Graphics，在设计区左右各画一条 4096 宽的深色矩形，把溢出部分盖掉。这样无论窗口多宽，画面都是干净的固定视口。

var g = frameNode.addComponent(Graphics);
g.fillColor = new Color(10, 13, 20, 255);
g.rect(-4096, -400, 4096, DESIGN_H + 800); g.fill();
g.rect(DESIGN_W, -400, 4096, DESIGN_H + 800); g.fill();

AS3 / Starling → Cocos 3.8 对照

需求 Starling (AS3) Cocos Creator 3.8
显示对象 Sprite / Image Node + Sprite
图集取帧 Assets.getAtlas().getTexture(name) SpriteFrame{rect, originalSize, offset}
纹理来源 Texture.fromBitmapData ImageAsset → Texture2D.image
顶层容器 Starling.current.stage Canvas（RenderRoot2D）
帧循环 Event.ENTER_FRAME Component.update(dt)
补间 Tween / TweenMax tween() 或手写插值
粒子 ParticleSystem ParticleSystem2D
音效 SoundMixer / SoundChannel 这个包里没 cc.audioEngine，直接用 new Audio()
屏幕震动 操作 stage 的相机 位移场景根节点
设计分辨率 Starling.multitouchEnabled + stage.stageWidth view.setDesignResolutionSize(w, h, SHOW_ALL)

最后一条值得说明：我一开始想让引擎的音频模块播 mp3，结果发现这个裁剪过的 web 包里没有 cc.audioEngine，于是直接用浏览器的 new Audio()。代价是自动播放策略：首次交互前不能出声，所以背景音乐挂在第一次 pointerdown 上才开始。

最后

原版是 2012 年的 Flash 游戏，Starling 当年解决的「GPU 加速 2D 精灵批处理」这件事，今天的 Cocos、LayaAir、Unity 的 UGUI 都在用同一套思路：一张图集、一个材质、按渲染顺序合批。换引擎之后真正会变的只有 API 名字，不会变的是合批条件、裁剪成本、以及「画不出来先看 draw call」这条排查路径。

原工程：Hemanth Sharma 的 Hungry Hero（Simplified BSD）。Cocos 版是我用脚本 + 手写代码搬过来的，如果你想看某个类的具体实现，可以邮件找我：cgengpeng@gmail.com。
