把 Hungry Hero 这个开源小游戏搬到 Cocos Creator 3.8

2026-11-01 Cocos Creator 2.6k 字
Cocos Creator 游戏开发 迁移 小游戏

鼠标移动控制主角高度，吃食物加分，躲障碍。画面小就点右下角 ⛶ 全屏，或在新窗口单独打开。

Hungry Hero 是我以前无意间刷到的一个开源小游戏，作者把源码和素材一起放了出来，协议是 Simplified BSD。玩法很朴素：玩家移动鼠标控制高度，吃食物、躲障碍，路上还有咖啡（加速，能撞穿障碍）和蘑菇（食物自动飞过来）两个道具。

我把它搬到了 Cocos Creator 3.8.8。这次没打算照着玩法重写一个——原项目就五个类，Welcome / InGame / GameBackground / Hero / Obstacle，我是挨个对着改的，图集矩形、音效、动画帧序、背景视差系数全部按原样抄。

搬过来的东西

原项目 现在
欢迎页主角从左侧滑入，标题、按钮 一样，缓动按原版 1.2 秒
5 种食物编队（波浪、直线、斜线、环形…） 按原 pattern 状态机写
4 种障碍，出现前 5 帧 “LOOK OUT!” 预警 都有，含红屏闪烁
撞击后主角翻转、扣命、屏幕震动 震动改成挪相机节点
咖啡加速撞穿障碍、蘑菇自动吸食 都有，各配一个粒子发射器
4 层视差背景（天空 0.02 / 山 0.2 / 楼 0.5 / 草 1.0） 照原项目的背景层逻辑抄，含取整和回卷
5 条命，分数 = 食物分 + 距离 —
暂停、静音、About、结算页 结算页三个按钮的坐标按原公式算的

原项目 assets/ 里就一张 2048×1024 的图集、两张 1024×768 背景、8 个 mp3，全部直接复用，一张图都没重画。

只用引擎运行包，场景用代码建

Cocos 3.x 正常流程是在编辑器里拖个场景再构建。但那样产物是场景资源加一堆序列化 JSON，我手上没有编辑器里手接的线，也不想手写 .scene 和 .meta（__type__ 要填压缩过的脚本 uuid，写错一个字符就打不开）。

所以换了个笨办法，把之前那个 Cocos UI 性能实验室 的运行包搬过来：cocos-js/ 是引擎本体，src/system.bundle.js 是 SystemJS，加上 polyfills.bundle.js 和 import-map.json，剩下的自己写。

  • index.js 里 System.import('cc') 拿引擎，cc.game.init({settingsPath}) → cc.game.run() → 加载 src/game.js
  • game.js 里 new Scene()、new Node()、addComponent(Sprite)，最后 director.runSceneImmediate(scene)

工程因此就是几个纯文本 js 加一堆图片，改一行刷新就见效，也能在无头浏览器里跑自动化。代价是编辑器平时替你做的事得自己补，而且补错的时候没有任何提示。

五个「白屏，控制台一片干净」的坑

每一个现场都一样：页面加载完了，画面什么都没有，控制台一句报错都没有。

1. 只有 Node 树，引擎根本不遍历

场景图是对的。director.getScene() 下 40 个节点，位置、尺寸、SpriteFrame 都正常，sprite._renderData 里 4 个顶点 6 个索引也在，requestAnimationFrame 也在跑（getTotalFrames() 涨到 416）。可 device._numDrawCalls 一直是 0。

翻了半天引擎源码才看到这句：

// cc.RenderRoot2D
onEnable() { director.root.batcher2D.addScreen(this); }
onDisable() { director.root.batcher2D.removeScreen(this); }

Cocos 3.x 的 2D 渲染是从 RenderRoot2D（Canvas 的父类）往下走的：它 onEnable 时把自己注册进 Batcher2D 的 _screens，渲染时只 walk 这几个 screen。纯 Node 树摆得再对也不在名单里。

所以 Canvas 这层省不掉：

var canvasNode = new Node('Canvas');
canvasNode.setPosition(DESIGN_W / 2, DESIGN_H / 2, 0);   // 放在设计区中心
scene.addChild(canvasNode);
canvasNode.addComponent(UITransform).setContentSize(DESIGN_W, DESIGN_H);

var camNode = new Node('Camera');
canvasNode.addChild(camNode);
var cam = camNode.addComponent(Camera);
cam.projection = Camera.ProjectionType.ORTHO;
cam.orthoHeight = DESIGN_H / 2;

var canvas = canvasNode.addComponent(Canvas);
canvas.cameraComponent = cam;      // Canvas 会把相机摆到自己的世界坐标 + z=1000

补一句：Canvas._onResizeCamera() 会按 windowSize.height / getScaleY() / 2 重算 orthoHeight，设计分辨率适配不用自己管。

2. 相机参数名写错，也不报错

我凭记忆写了 cam.ortho = true; cam.nearClip = 1; cam.farClip = 3000;。这三个属性都不存在，JS 不会报错，只是默默变成普通字段。相机于是保持默认的透视投影、near=1 / far=1000，而相机节点在 z=1000，精灵都在 z=0，正好压在远裁面上，裁得一个不剩。

3.8 里正确的名字：

cam.projection = Camera.ProjectionType.ORTHO;   // 0
cam.orthoHeight = DESIGN_H / 2;
cam.near = 1;
cam.far  = 3000;

之所以敢断定问题在相机不在贴图，是因为 cc.director.root.device._numDrawCalls 一直是 0——连提交都没提交。

3. node.setScale(1) 会让节点消失

原项目里写 hero.scaleX = hero.scaleY = 1，我顺手写成 heroNode.setScale(1)。Cocos 的 setScale 要三个参数，缺的 y、z 是 undefined，局部矩阵算出来是 NaN。节点还在场景里，activeInHierarchy 是 true，worldPosition 也读得到，就是不画。

更麻烦的是子节点跟着坏：两个粒子发射器的 worldPosition 变成 NaN，我一开始以为是粒子系统把合批缓冲搞脏了，绕了很久。

heroNode.setScale(1);                    // ✗ 隐形
heroNode.setScale(1, 1, 1);              // ✓
heroNode.setScale(new cc.Vec3(1, 1, 1)); // ✓

后来把工程里所有 setScale 搜了一遍，又抓出 setScale(p.scale) 和 setScale(w.scale, 1) 两处，都是缺参数的。

4. 运行时贴图要的是 ImageAsset

图集是运行时用 <img> 加载的，直接 texture.image = img 会炸：

TypeError: i.extractMipmaps is not a function

image 的 setter 内部是 this.mipmaps = [t]，而 mipmaps 的 setter 会对每个元素调 extractMipmaps()，这方法只有 ImageAsset 上有。得先包一层：

var imageAsset = new cc.ImageAsset();
imageAsset._format = 35;        // RGBA8888
imageAsset._nativeData = img;   // 注意：data 在这个构建里是只读 getter
var t = new cc.Texture2D();
t.image = imageAsset;
t.packable = false;

3.8.8 的 web 包里 data 只定义了 getter（imageAsset.data = img 会报 “only a getter”），所以直接写 _nativeData，data 的 getter 返回的就是它。

5. SpriteFrame.offset 的符号是反的

从 TexturePacker 的 XML 切帧时，裁剪帧要算 offset。我按左上角原点的习惯写成：

f.offset = new Vec2(s.ox + s.w / 2 - s.ow / 2, s.oy + s.h / 2 - s.oh / 2);   // ✗

小图看不出（差 1~3 像素），但背景层 bgLayer2 上下各裁了 26 和 44 像素，整层被顶上去 26px，接缝全露出来，看着像贴图位置摆错了。

Cocos 的语义是：offset = 裁剪内容相对原图中心的位移，x 向右为正，y 向上为正；TexturePacker 的 frameX/frameY 是从左上角量起的负 padding。对应过来：

// offset.x = trimLeft - (ow - w)/2      trimLeft = -frameX
// offset.y = (oh - h)/2 - trimTop       trimTop  = -frameY
f.offset = new Vec2(-s.ox - (s.ow - s.w) / 2, (s.oh - s.h) / 2 + s.oy);

另外两个 SystemJS 的坑

  • chunks/bundle.js（里面注册了 rollupPluginModLoBabelHelpers）必须用经典 <script> 标签加载，而且排在 system.bundle.js 后面。它本来是给引擎 main 包的 preload 用的，运行时模式下那段永不执行，用 System.import() 拉也不生效——抓包看过，一次请求都没发出去。
  • 这套 SystemJS 里，./xxx 相对的是页面目录，不是模块自己所在的目录。所以 src/application.js 里要写 System.import('./src/game.js')，写成 ./game.js 会 404。

背景视差

原项目的背景层逻辑挺干净，直接抄过来（下边是它的伪代码，stageWidth / stageHeight 就是画布宽高）：

// 每层 = 两张同图，左边缘对齐在 0 和 w
image1.x = 0;            image1.y = stageHeight - image1.height;
image2.x = image2.width; image2.y = image1.y;

// 整层左移，超过一个宽度就回卷
bgLayer.x -= Math.ceil(speed * parallaxDepth);
if (bgLayer.x < -stageWidth) bgLayer.x = 0;

两处容易摆错：

  1. 底部对齐（stageHeight - image.height），不是垂直居中；
  2. 接缝要落在右边界上，也就是第二张图的左边缘在 w。

我一开始按 x = 0 和 x = w 摆中心，接缝就跑到画面正中间了。bgLayer2 是两边渐隐的软山丘，本来就不是给无缝平铺画的，接缝一进画面就是一条亮带。改成左边缘对齐之后，接缝从右边界开始往左走，观感跟原版就一致了。

顺手量了下草层 bgLayer4 的左右边缘像素，完全一样，能无缝平铺；bgLayer3（楼）最大差 8；bgLayer2 差得多。所以这不是代码写错了，是素材本身就那样，照原版的摆法就不会难看。

跑起来之后的数字

场景 Draw Calls 三角面
游戏进行中（4 层背景 + 主角 + 30+ 食物 + 障碍） 12 ~ 13 164 ~ 234
结算页 12 150

所有精灵共用一张 2048×1024 图集和同一个材质，食物、障碍、主角合在一批；4 层背景各是一张图，拆成 4 批；再加 2 批左右的 HUD 文本。物体数量翻倍，批次数基本不动。

HUD 用的是系统字体 Label，每个实例带自己的动态字型纹理。这儿一共 6 个 label，无所谓；要做几十行的列表就得换位图字体了。

设计分辨率和黑边

页面用 SHOW_ALL 把 1024×768 的设计区等比塞进任意窗口，多出来的是黑边。可背景层是横向平铺的，会铺到设计区外面去，左右两侧露出来的内容跟里面接不上，一条硬缝正好压在设计区边界上。

办法很土但省事：在最后一个兄弟节点上挂个 Graphics，在设计区左右各画一条 4096 宽的深色矩形，把溢出部分盖掉。窗口多宽画面都是干净的固定视口。

var g = frameNode.addComponent(Graphics);
g.fillColor = new Color(10, 13, 20, 255);
g.rect(-4096, -400, 4096, DESIGN_H + 800); g.fill();
g.rect(DESIGN_W, -400, 4096, DESIGN_H + 800); g.fill();

写在最后

这类小游戏的核心都是批处理：一张图集、一个材质、按渲染顺序合批，今天的 Cocos、LayaAir、Unity UGUI 还是同一套做法。所以搬这一遍下来，真正省时间的不是 API 怎么对应，而是排查路径——白屏、控制台干净、draw call 是 0，基本就能把范围锁到相机或者渲染根上，跟具体引擎关系不大。

原项目是一个开源小游戏（Simplified BSD）。Cocos 版是我用脚本加手写代码搬的，想看某个类的具体实现可以邮件找我：cgengpeng@gmail.com。
