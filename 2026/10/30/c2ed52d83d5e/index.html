用 Cocos Creator 复刻我的 UI 性能实验室

2026-10-30 1.6k 字
性能优化 Cocos Creator UI

之前用 Unity WebGL 做过一个在线性能实验室，把虚拟列表、合批、对象池、遮罩断批、帧率分布这些 UI 性能的关键机制做成了可实时调参的实验。这次把其中三个核心实验用 Cocos Creator 3.8 复刻了一遍，一是验证这些机制在 Cocos 里的表现，二是正好系统地过一遍 Cocos 的组件模型和 API。

三个实验：虚拟列表（10 万条数据）、伤害飘字 + 对象池、合批对比开关。全部代码贴在文中，可直接放进 3.8 项目跑。

先说结论

三套机制在 Cocos 里的行为和 Unity 几乎一致，验证了它们是渲染架构层面的通用规律，不是某家引擎的专利：

机制 解决的问题 Cocos 侧实现
虚拟列表 元素太多 content 高度撑满 + 滚动反算可见区间 + 节点池复用
对象池 频繁创建销毁 → GC 峰值 飘字上飘结束后回池，instantiate/destroy 次数归零
合批 批次太多 160 个 Sprite 共享图集 = 个位数 Batch，独立纹理 = 160+

顺带一提 Cocos 3.8 的调试面板很方便：debug.setDisplayStats(true) 就能在预览窗口左下角看到 FPS 和 DrawCall，做这类实验连 Profiler 都不用开。

实验一：虚拟列表

10 万条数据，常驻节点只有十几个。核心就三件事：

  1. content 高度撑满真实数据高度 —— 滚动条的长度和手感才对
  2. 监听 scrolling 事件，由 content.position.y 反算当前可见区间 [first, last]
  3. 区间外的节点回池，区间内的从池里取出摆位 —— 滚动过程零创建零销毁
@ccclass('VirtualList')
export class VirtualList extends Component {
    @property(ScrollView) scrollView: ScrollView = null!;
    @property(Prefab) itemPrefab: Prefab = null!;
    @property totalItems = 100000;
    @property itemHeight = 48;

    private pool: Node[] = [];
    private active: { node: Node, idx: number }[] = [];

    onLoad() {
        const content = this.scrollView.content!;
        // 1. 撑满真实高度
        content.getComponent(UITransform)!.height = this.totalItems * this.itemHeight;
        this.scrollView.node.on('scrolling', this.refresh, this);
        this.refresh();
    }

    private refresh() {
        const offset = -this.content.position.y;   // 已滚动像素
        const viewH = this.scrollView.node.getComponent(UITransform)!.height;
        const first = Math.max(0, Math.floor(offset / this.itemHeight) - 1);
        const last = Math.min(this.totalItems - 1, Math.ceil((offset + this.viewH) / this.itemHeight));

        // 回收区间外的
        for (let i = this.active.length - 1; i >= 0; i--) {
            const it = this.active[i];
            if (it.idx < first || it.idx > last) {
                this.recycle(it.node);
                this.active.splice(i, 1);
            }
        }
        // 补齐区间内的
        for (let i = first; i <= last; i++) {
            if (this.active.some(a => a.idx === i)) continue;
            const n = this.acquire(i);
            n.setPosition(0, -i * this.itemHeight, 0);  // item anchor = (0.5, 1)
            this.active.push({ node: n, idx: i });
        }
    }

    private acquire(idx: number): Node {
        const n = this.pool.pop() ?? instantiate(this.itemPrefab);
        n.setParent(this.content);
        n.getComponent(Label)!.string = `第 ${idx + 1} 条`;
        return n;
    }

    private recycle(n: Node) { n.removeFromParent(); this.pool.push(n); }
}

做对照模式时故意留了个反例开关：全量创建 3000 个节点直接滚动 —— 卡顿肉眼可见，和虚拟模式的丝滑形成对比。10 万条全量创建连试都不用试。

一个移植细节：item 节点的 Anchor 必须设成 (0.5, 1)（顶部中间），摆位公式 -index * itemHeight 才成立。Unity 的 RectTransform 锚点体系在这就能直接平移过来。

实验二：伤害飘字 + 对象池

点击屏幕喷一波飘字（40 个），上飘渐隐后结束生命周期。两个模式对比：

  • 池化模式：结束后 removeFromParent 回池，Gc 计数纹丝不动
  • new/destroy 模式：每次 instantiate + destroy，计数狂涨 —— 对应的就是 GC 峰值和掉帧
private spawnOne() {
    let n: Node;
    if (this.usePool && this.pool.length > 0) {
        n = this.pool.pop()!;
    } else {
        n = instantiate(this.floatPrefab);
        this.churn++;                    // 只有新建才计入
    }
    // ... 摆位、随机伤害数字
    tween(n).by(0.9, { position: new Vec3(0, this.floatHeight, 0) }).start();
    tween(op).delay(0.3).to(0.6, { opacity: 0 }).call(() => {
        Tween.stopAllByTarget(n);
        if (this.usePool) {
            n.removeFromParent();        // 回池，不销毁
            this.pool.push(n);
        } else {
            n.destroy();
            this.churn++;
        }
    }).start();
}

容易漏的一行：从池里复用节点前必须 Tween.stopAllByTarget(n)，否则上一个生命周期的 tween 还挂着，复用时会串动画。这类坑在 Unity 里对应的是协程没停干净就回池，一个道理。

对象池解决的是「频繁创建销毁 → GC 峰值 → 掉帧」，和虚拟列表（元素太多）、合批（批次太多）不是一回事，三个问题经常被混为一谈。

实验三：合批对比开关

160 个 Sprite 网格排布，一个按钮切换两种模式：

  • 共享图集：全部引用同一个 SpriteFrame → DrawCall 个位数
  • 独立贴图：运行时为每个 Sprite 生成一张独立纹理 → DrawCall 160+
// 运行时造一张 16x16 纯色纹理，每张颜色不同，强制断批
private makeUniqueFrame(i: number): SpriteFrame {
    const tex = new Texture2D();
    tex.reset({ width: 16, height: 16, format: Texture2D.PixelFormat.RGBA8888 });
    const data = new Uint8Array(16 * 16 * 4);
    const c = new Color();
    Color.fromHSV(c, (i * 0.618) % 1, 0.75, 0.95);
    for (let p = 0; p < 256; p++) {
        data[p * 4] = c.r; data[p * 4 + 1] = c.g; data[p * 4 + 2] = c.b; data[p * 4 + 3] = 255;
    }
    tex.uploadData(data);
    const sf = new SpriteFrame();
    sf.texture = tex;
    return sf;
}

在调试面板里切换按钮，DrawCall 数字从个位数跳到 160+ 再跳回来，这就是合批的全部本质：同材质同纹理的物体合成一个绘制批次。断批三要素 —— 不同纹理、不同材质参数、遮挡组件（Mask 的 stencil 写入）—— 前两个这个实验直接演示了。

之前在 Unity 实验室里验证过 Mask 比 RectMask2D 恒定多 2 个批次（stencil 写入 + 还原），Cocos 的 Mask 组件同样是 stencil 方案，这个结论可以直接迁移。

从 Unity / LayaAir 过来的映射表

这次复刻顺手整理的心智映射，对两边都有经验的人应该是最快的上手路径：

Unity LayaAir Cocos Creator 3.x
GameObject Sprite/Node Node
MonoBehaviour 组件基类 Component（onLoad/start/update 几乎同名）
Prefab 预制 Prefab
RectTransform 锚点系统 UITransform
AssetBundle 加载策略 Bundle
Coroutine Tween tween / Tween 类
SpriteAtlas 图集 SpriteAtlas / 动态合图

引擎 API 只是名字不同，渲染架构和性能机制是相通的：批次怎么合、GC 什么时候炸、列表怎么复用，这些问题在任何 2D 引擎里都长一个样。
