LayaAir 原生 vs Unity 原生 — 为什么你的 Worker 在原生 App 里不启用

2026-06-09 638 字
LayaAir Unity WebView Worker 游戏引擎

LayaAir “原生” 到底是什么？

LayaAir 的”原生”（LayaNative）和 Unity 的原生是两码事。

LayaAir 原生（LayaNative）

┌─────────────────────────┐
│    原生 Shell (APK/IPA)  │
│  ┌───────────────────┐  │
│  │   JS 引擎 / WebView │  │  ← TS/JS 代码跑在这里
│  │   游戏逻辑          │  │
│  └───────────────────┘  │
└─────────────────────────┘

本质上是一个原生壳包了一个高性能 WebView（或者直接嵌入 V8/JSC 引擎），游戏代码还是 JavaScript 在跑，并没有编译成机器码。

Unity 原生（IL2CPP）

┌─────────────────────────────┐
│    原生可执行文件              │
│  C# → IL → C++ → 机器码      │  ← 真·编译成原生二进制
│  直接调用 GPU API (Metal/Vulkan) │
└─────────────────────────────┘

关键差距对比

维度 LayaAir 原生 Unity 原生
运行方式 JS 解释 / 即时编译 预编译机器码
GPU 调用 通过 WebGL → 桥接 直接调 Metal/Vulkan
内存管理 JS GC + WebView 开销 手动管理 + IL2CPP GC
性能上限 受 JS 引擎限制 接近原生 C++

那为什么还叫”原生”？——只是说发布出来是个 APK/IPA，能上应用商店。骨子里还是 H5 那一套。

为什么 LayaAir 原生 App 不启用 Worker？

回到你代码里的现象：Worker 只在小游戏平台开启，浏览器也只给一个标准 Worker 兜底，Android/iOS 原生发布时不启用 Worker。 原因有三：

1. WebView 对 Worker 支持不稳定

Android/iOS WebView 的 Worker 实现有很多坑：

  • 系统内置 WebView 的 Worker 线程崩溃后不会像微信那样自动重建
  • 存在内存泄漏、消息丢失等问题
  • 不同系统版本表现不一致

2. 原生 App 有多线程能力

真需要多线程，可以直接用原生层（Java/Kotlin/Swift）开线程，不需要在 WebView 里搞 Worker，属于脱裤子放屁。

3. 性能确实够

原生 App 的 JS 引擎（JSC/V8）性能比小游戏容器好，而且没有小游戏平台的各种沙箱限制和中间层开销，主线程算战斗通常也够快。

小游戏为什么需要 Worker？

微信/抖音小游戏跑在平台的 JS 容器里：

  • 没有原生多线程可调用
  • 平台要求不能卡 UI
  • 只能靠 wx.createWorker 来曲线救国

所以代码里只在小游戏平台开 Worker，浏览器也只给一个标准 Worker 兜底——这是平台限制下的权衡，不是”原生性能好不需要”。

一句话总结

LayaAir 的”原生” = 给 H5 套个 APK 壳，跟 Unity 那种编译成机器码的真正原生完全不是一回事。WebView 里的 Worker 本身就多一层坑，再加原生壳，问题更多，不如直接用原生线程。
