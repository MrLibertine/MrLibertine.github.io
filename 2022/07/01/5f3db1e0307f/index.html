为什么我们把 Lua 热更新迁移到 ILRuntime

2022-07-01 2.2k 字
Unity C# ILRuntime Lua 热更新

背景

Unity 项目做热更，过去几年大家基本都选 Lua。xLua、ToLua、sLua 三套方案，用的人多，踩坑文章也多。我们的项目也一样——战斗逻辑、UI、网络协议，全用 Lua 写的，通过 ToLua 和 C# 互调。

但项目写了快两年，Lua 代码越来越多，改一个功能要跨两门语言来回跳，维护起来越来越吃力。我们花了三个月调研和试跑，最终决定把热更方案从 Lua 换成 ILRuntime。这篇文章把当时怎么想的、怎么做的、踩了什么坑记下来。

Lua 方案哪里不好用

1. 要同时写两门语言

C# 和 Lua 差别太大了。C# 是静态类型，编译期就能发现传错参数；Lua 是动态类型，传了个 nil 进去只能运行时崩。

结果就是：日常开发脑子里要记两套规则，查 bug 要开两个调试器，C# 一个 Lua 一个。一旦 bug 出在 C# 调 Lua 或者 Lua 调 C# 的边界上，两边调用栈是断的，只能靠猜。

还有错误处理方式不统一。C# 用 try-catch，Lua 用 pcall。Lua 里抛的错传到 C# 会丢掉栈信息，线上 crash 定位起来非常花时间。

2. C# 和 Lua 互相调用太慢了

每次 C# 调 Lua 函数，代码长这样：

LuaFunction func = luaState.GetFunction("BattleSystem.OnDamage");
func.BeginPCall();
func.Push(attackerId);
func.Push(targetId);
func.Push(damage);
func.PCall();
func.EndPCall();

参数要一个一个 Push 进去，完事还要 EndPCall。不光写起来烦，还有三个性能问题：

  • 值类型装箱：int、float 这种值类型传过去会临时装箱，产生 GC 垃圾
  • 字符串拷贝：C# string 和 Lua 的 char* 互转，每次都要分配新内存
  • 委托注册：C# 的方法暴露给 Lua 要注册委托，委托对象本身也是 GC 负担

战斗中一帧可能要跨语言调几千次，GC 一多帧率就掉。

3. 工具链太弱

  • 没有编译检查。改了个函数名，调用方不会报错，跑起来才发现传了个 nil
  • 想重命名一个变量，只能用全局搜索替换，漏掉一个就出 bug
  • 代码补全不好用。C# 的类在 Lua 里怎么提示全靠 EmmyLua 注解维护，经常跟不上
  • 没有包管理器。用个第三方库基本就是下载 zip 拷进来

4. 新人上手慢

招进来的 Unity 开发，C# 本来就熟，但要学会写 Lua 热更代码，还得搞清楚 ToLua 怎么桥接 C# 类、项目自己的 Lua 框架怎么搭的。这个阶段一般要一两周。

为什么选了 ILRuntime

ILRuntime 干的事可以一句话说清楚：热更代码也用 C# 写，编译成 DLL，运行时由 ILRuntime 解释执行，不用换语言。

对比

Lua ILRuntime
热更用什么语言写 Lua C#
类型检查 没有，跑起来才知道 编译期就能查出来
跨语言调用 Push/Pop 栈操作，有装箱 委托或适配器，无装箱
调试 单独的 Lua 调试器 跟主工程用同一个 VS / Rider
热更代码能不能直接用主工程的类 不能，要写桥接层 可以，直接 using 引用
包体增加 +2.1MB（Lua 解释器） +0.8MB（ILRuntime）

具体好在哪

只写一门语言

不用在 C# 和 Lua 之间切来切去。热更代码和主工程都是 C#，类型系统是一致的，改接口的时候编译器会立刻标红所有受影响的调用。

调试不再折腾

ILRuntime 的热更 DLL 可以直接在 VS 或 Rider 里打断点。主工程的代码和热更代码的调用栈在同一个窗口里，从断点一步一步走就能定位问题，不用再猜。

跨语言调用快了很多

用 ILRuntime 后，热更代码调主工程是这样：

// 热更 DLL 里直接写，跟写普通 C# 没区别
public class BattleSystem : ILogicSystem
{
    public void OnDamage(int attackerId, int targetId, float damage)
    {
        var target = EntityManager.GetEntity(targetId);
        target.GetComponent<HealthComponent>().TakeDamage(damage);
        EventBus.Emit(new DamageEvent(attackerId, targetId, damage));
    }
}

没有 Push / Pop，没有装箱，没有字符串拷贝。跨边界的开销基本只剩一次适配器分发，跟 Lua 方案比小了一个量级。

可以直接复用主工程的代码

热更 DLL 里直接 using 主工程的命名空间，用主工程定义的接口、类型、工具类。不需要像 Lua 那样子给每个要用到的 C# 类写镜像表和桥接代码。

性能实测

在 iPhone 12 和红米 K40 上跑了一组对比：

场景 Lua ILRuntime 改善
单帧跨语言调用 5000 次 3.2ms 0.8ms 快 4 倍
战斗初始化 180ms 95ms 快近一半
战斗状态每帧 GC 12.4KB 3.1KB 少 3/4

并不是说 ILRuntime 解释执行本身比 Lua JIT 快。之所以整体更快，是因为省掉了跨语言 Marshalling 的开销，也没有双 GC（Lua 一个、C# 一个）同时跑。

怎么迁的

整体花了 12 周，3 个开发。

第一周到第二周：小范围试跑

搭好 ILRuntime 基本环境，验证类继承、接口、泛型、委托、协程这些核心功能能不能跑通。选了一个独立的设置界面模块移植过去，确认全套流程没问题。

第三周到第五周：搭框架

  • 定义热更层要用到的接口（ILogicSystem、IView、IDataModel 等）
  • 把主工程需要暴露给热更的类型注册好 Adapter
  • 热更 DLL 的下载、校验、加载流程替换掉原来 Lua 那套

第六周到第十一周：搬业务代码

按”网络协议→数据层→战斗逻辑→UI 层”的顺序，一个模块一个模块搬。每搬完一个，先保留 Lua 旧版，用开关控制跑新版还是旧版，确认稳定了再全量切。

第十二周：清理

全量切到 ILRuntime 后，删掉项目里所有 Lua 代码和 ToLua 桥接层。包体小了 2.1MB。

踩过的坑

1. 泛型支持不完整

ILRuntime 的泛型没有原生 CLR 那么全。List<T> 之类的基础容器能用，但自定义泛型类加泛型方法组合有时会炸。

处理方式：

  • 尽量用主工程已经注册好的泛型类型
  • 自定义泛型在主工程里包一层具体类型再暴露出去
  • 别在热更新里用 MakeGenericType 动态造泛型

2. 反射比原生慢

ILRuntime 里的反射比 CLR 原生反射慢一个数量级。高频调用的地方不能用反射，要用 Adapter 预先绑定。

// 主工程里提前注册，避免热更侧运行时反射
appDomain.RegisterCrossBindingAdaptor(new BattleSystemAdapter());
appDomain.RegisterCrossBindingAdaptor(new EntityManagerAdapter());

3. 自定义 struct 跨边界有拷贝开销

虽然没装箱了，但自定义 struct 跨主工程和热更 DLL 传递仍然会拷贝一份。原则：

  • 跨边界的 struct 控制在 4 个字段以内
  • 大的数据结构用 class
  • Vector3、Quaternion 这种引擎内置的 ILRuntime 已经优化过，正常用

4. 调试器和 Unity 版本的兼容

ILRuntime 调试器依赖 Mono.Cecil，Unity 2021 以上版本要手动调 Assembly Definition 的引用关系，不然符号加载会失败。最好在试跑阶段就定好版本组合。

换成 ILRuntime 之后的变化

之前（Lua） 之后（ILRuntime）
新人上手 1-2 周 2-3 天
线上 bug 定位 4-6 小时 半小时到一小时
战斗中帧率（中端机） 42-48 FPS 55-60 FPS
每帧 GC 12.4KB 3.1KB
编译期类型检查 没有 有
包体增加 +2.1MB +0.8MB

什么情况不用迁

不是所有项目都适合换 ILRuntime。这些情况继续用 Lua 更合适：

  1. 团队 Lua 已经用得很熟了，有自己的一套框架和工具，重写一遍不值当
  2. 热更代码就那么几行配置脚本，引入 ILRuntime 属于杀鸡用牛刀
  3. 项目需要跟外部的 Lua 代码配合（比如和 Cocos2d-x 共享同一套逻辑层）
  4. 目标平台对 IL2CPP 加反射有硬限制，需要提前验证 ILRuntime 能不能跑

总结

换 ILRuntime 最大的原因不是它跑得更快，而是只用一门语言写代码这件事省太多事了。不用在 C# 和 Lua 之间折腾、一个调试器就能看到完整调用栈、改了接口编译期就报错——这些东西在日常开发中的价值比跑分差距大得多。

如果你们的 Lua 项目也陷入了跨语言调试花时间、新人上手慢、维护越来越累的困境，可以认真评估一下 ILRuntime。但动手之前一定先把试跑做透：泛型支持到什么程度、反射性能够不够、目标平台能不能跑通，这三样是决定成败的关键。
